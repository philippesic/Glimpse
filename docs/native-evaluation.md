# Native application evaluation

Use this guide when improving Glimpse's UI or evaluating its end-to-end experience. It defines repeatable native computer-use walkthroughs and an evidence-based improvement loop. It does not start or resume a development campaign. Sustained overnight work needs an explicit execution request and preserves existing resource and pause controls.

[glimpse.md](../glimpse.md) remains the product and feature authority; [UI design](ui-design.md) governs presentation. Use their existing correctness and performance requirements rather than inventing replacement targets. [Qualification](qualification.md), the [feature matrix](feature-matrix.md), and the private current checkpoint distinguish implemented behavior from verified results. A reference application's behavior does not override Glimpse's file safety or single-directory-list model.

## Evaluation criteria

Qualify the actual GPUI application on the declared platform. Linux evidence does not qualify macOS. Keep shared design platform-neutral and isolate OS behavior in small platform modules. The retired egui/AppKit implementation and historical qualification results do not establish GPUI behavior.

Evaluate platform interface conventions, WCAG 2.2 text contrast and keyboard access, consistent spacing and typography, alignment, visible focus and states, readable text without clipping or overlap, and clear, efficient core workflows. Reference applications may inform design but are not acceptance requirements. No installed Mac application or screenshot comparison is required for Linux qualification.

Record each defect against an observable criterion and a reproducible task. Separate appearance, usability, functionality/safety and performance. A numerical score cannot compensate for a failed or unverified required check. Performance targets and workloads remain those in [glimpse.md](../glimpse.md); do not change them to improve results.

## Session and evidence setup

1. Read the private `.local/CURRENT.md`, relevant design sections and existing ownership before acting. Preserve paused work and other sessions. Record the authorized scope and any actual deadline; do not attribute an agent-chosen boundary to the user. On shared hosts follow installed host/device policy. Keep other sessions and services untouched.
2. Verify the repository root and inspect changes. Keep a recoverable source baseline and runnable baseline build before implementation; do not assume Git captures untracked source. Record source and executable identities privately. Do not install over `/Applications/Glimpse.app` just to test a candidate.
3. Create a unique ignored `.local/ui-evaluation-<run>/` directory with `fixtures/`, `data/`, `baseline/` and `candidate/`. Preserve fixture originals and a manifest of exact initial bytes. Use separate fixture and data copies for baseline and candidate so edits, recents, recovery or preferences cannot contaminate comparisons.
4. Build a release candidate using the README's commands. Launch the intended native executable with `GLIMPSE_DATA_DIR` set to the run's absolute `data/` path and an explicit fixture path. For example, from the repository root: `GLIMPSE_DATA_DIR="$evaluation_dir/data" "$PWD/target/release/glimpse" "$evaluation_dir/fixtures"`, where `evaluation_dir` has been assigned the absolute run directory. Identify the resulting GUI process/window; CLI launcher exit does not mean the GUI exited. Keep background mode off for visible interaction checks.
5. Use application preferences for appearance tests. Do not change global desktop settings or personal app configuration casually; back up personal configuration and follow the shared-settings hash check before editing it. Avoid closing or modifying user-owned windows.

Keep screenshots, action records, measurements, raw logs and reviewer output private under the run directory. Promote only concise edited conclusions into project documentation. A small run manifest should identify source/build, fixture/settings versions, machine/OS/display, criteria and evidence set, owned resources and scenario results.

### Fixture contract

Prepare deterministic disposable content before the baseline; keep its generator or exact manifest with the evidence. Include:

- `project-a/` and `project-b/` with duplicate basenames, a three-level folder path, long names with spaces, hidden configuration, an ignored subtree and an empty folder. Include unique filename and content-search markers in each scope.
- A normal source file, unknown-extension plain text, a long scrollable document, UTF-8/BOM/CRLF/final-newline variants, and combining accents, CJK text and emoji. Keep reference text identical across builds.
- Markdown with headings, paragraphs, lists, a table, tasks, fenced code, local image and relative link; include raw HTML and a remote-image URL to check safe rendering behavior. Use a generated tiny local image rather than a download.
- Separate copies for rename/Trash, Save As/Copy, external replacement, stale search hits and crash recovery. Include unsupported binary and over-limit input.
- Generate large directories and the supported-size/long-line performance fixtures only for the relevant measurement pass. Keep setup costs outside measured intervals. Real mounts, permission loss, IME and screen-reader access require their own supported execution route; a synthetic substitute does not qualify them.

### Computer-use discipline

Drive the actual native application. Browser previews, HTML mockups, internal state changes and unit tests do not substitute for desktop interaction.

For the unified computer-use tool, start with exactly one supported entry call, such as `await cua.getApp("Glimpse");`, or `await cua.getState();` when an inventory is needed. Read the returned API documentation before issuing further calls. After a resumed computer-use context, use the tool's documentation refresh as instructed. Do not invent methods or selectors. Other providers should use their documented native desktop adapter and record which adapter was used.

Verify the target executable/window, especially when multiple builds share the same app name. Prefer accessible names/roles and current snapshots; use observed screenshot coordinates when semantics are unavailable. Refresh observations after layout changes. Perform short action groups and check the resulting state before continuing. If an accessibility click does not focus a field, verify with a pointer route and report the semantics problem separately. Do not silently work around failures when scoring the normal route.

Use shell/file tools for fixture preparation, deliberate external-writer events, byte verification and instrumentation. Use computer input for the interaction being evaluated; do not set internal app state to skip it. Record adapter failures separately from app failures, investigate ambiguous cases, and count an unexecuted step as unverified. If native control is unavailable, raise a real structured pending question, continue independent authorized work, and make no native acceptance claim.

For every scenario record: start state, input route, actions, expected outcome, observed outcome, evidence paths, and `pass`, `fail`, `blocked` or `unverified`. Capture full-window screenshots at key checkpoints, including open popups and dialogs. Preserve unedited originals; crops may explain details but must not hide neighboring defects. Screenshots document state, not successful interaction or saved bytes.

## Walkthroughs

For a broad UI evaluation or release qualification, run the complete tour on the baseline before changing UI. For a focused change, select the affected scenarios and relevant safety and reverse-state checks. Use ordinary visible controls first, then repeat applicable routes using keyboard/menu commands. Record current names/routes so later agents can reproduce them, but keep expected outcomes stable if control placement changes. A missing required control is a finding, not a reason to remove a scenario.

| ID | Actions in the native app | Required observation and verification |
| --- | --- | --- |
| W01 Open and orient | Launch into fixtures; inspect the empty document area, current location and available actions. Use Open File and Go to Folder dialogs; cancel each before opening a file. | First useful state is legible; location and next action are evident; cancellation restores focus without changing content. |
| W02 Traverse and return | Enter three nested folders by pointer; scroll each list; select a sibling; use breadcrumbs, Parent, Back/Forward and Home. Repeat traversal with arrows/Return. Inspect Volumes without mounting anything. | Predictable selection and retained independent scroll; sibling replacement is correct; no implicit scan or unwanted project setup. Confirm that each entry replaces the single list. |
| W03 Path access | Command-L, replace the full path, complete a directory with Tab, open another scope, then cancel another entry with Escape. Copy absolute and relative paths; paste into a disposable field and check exact paths. Try a missing path. Drop a disposable file/folder when supported. | Full-path access, correct resolution and useful failure; no accidental edit or stale focus. Missing-path entry creates nothing. |
| W04 Preview and settle | Click several similar files, explicitly keep one tab, edit another preview, switch duplicate-name tabs, then use directory navigation and Reveal in Navigator. | Clean preview replacement; editing pins; dirty text survives; names disambiguate; navigation and editing preserve context, caret, selection, scroll and undo. |
| W05 Edit and save | Select words/lines and Unicode graphemes, type, clipboard, undo/redo, indent/unindent, toggle wrapping, scroll and switch tabs. Save, reopen and compare bytes. Exercise an untouched BOM/CRLF file too. | Familiar editing and retained state; correct dirty/status display; exact intended edits and unchanged bytes for untouched saves. Paste is not an IME test. |
| W06 Document Find | Command-F; search multiple matches, change case/whole-word options, reveal Replace, Replace All, Undo, Go to Line, dismiss, and type again. | Current-buffer search, visible match/selection distinction, sensible focus order; replacement/undo correct; dismissal returns to editor. |
| W07 Scope and search | Filter a folder, then Find Files and Find Text. Pin project-a, browse/open project-b, inspect out-of-scope identity; open a result, then Reveal separately. Exercise temporary scope, unpin, rapid query change, cancellation and no-match results. | Filter and recursive search remain distinct; actual scope/source/exclusions/coverage are clear; search activation does not move Location; stale work cannot replace current results. Create a stale hit externally and verify activation preserves dirty text. |
| W08 Filename index | Explicitly index one fixture scope; query as typed, change a fixture externally, inspect stale state, rebuild and remove. | No automatic crawl; bounded and honest coverage; stale snapshot clearly distinguished from rebuilt results. |
| W09 Read Markdown | Open as source, make an unsaved edit, switch Read/Edit, follow a disposable relative link, inspect table/code/image overflow and return to editing. | Reading reflects current buffer, preserves source and position; hierarchy and measure work; raw HTML does not execute and remote images are not fetched automatically. |
| W10 Create and manage | New draft then Save; New Named File and New Folder; attempt existing names; close a disposable file, rename and Trash it. Use Copy Path, Reveal in OS and Open Externally with disposable content. | Clear targets, useful menus, no clobber, correct destination bytes and OS Trash behavior. External apps open only by explicit action. |
| W11 Save decisions | Exercise Save As and Save Copy to new and existing disposable destinations. Close a dirty tab using Cancel, then Save; repeat with Discard on a separate copy. Repeat Quit/Cancel and Quit resolution in an owned session. | As rebinds only on success; Copy retains binding; cancellation preserves work; dirty decisions clearly name affected documents. Verify bytes and reopen. |
| W12 External changes | Replace a clean fixture externally and return to app, then Undo refresh. With another dirty fixture, replace externally; inspect Compare, cancel, Save Copy, and explicit reload/overwrite decisions on separate copies. Change disk again after a decision is shown. | Local work and observed disk version remain distinguishable; excerpts/truncation are honest; a stale overwrite decision is rejected. Verify final bytes independently. |
| W13 Recovery and failure | Persist a unique dirty marker in an isolated session; verify its recovery record before terminating only the owned GUI. Relaunch with the same isolated data, restore, save and relaunch again. Inspect history/storage management. Try unsupported input and controlled failed operations. | Recovery restores exact dirty content without silently overwriting disk or recurring after resolution; failures offer useful safe actions. Use fault-injection fixtures for disk-full/save-stage failures, never fill the real disk. |
| W14 Settings and commands | Visit every category and menu; search the command palette for core actions. Change theme, density, typography, line height, wrapping, navigation/search settings and one safe keybinding; test Apply, Cancel, Reload/reset where available, and restart persistence. | Controls are functional, discoverable and legible; no inaccessible category/actions, invalid settings loss or shortcut conflict. Check palettes/menus against required actions rather than just registered commands. |
| W15 Adaptation and access | Resize wide → ordinary → narrow → wide; drag divider; test tab overflow and long paths. Exercise window dragging, minimize/restore and fullscreen. Repeat key states in light/dark, compact/comfortable and larger text. Test keyboard-only navigation, dialog containment, Escape, inactive selection and Reduce motion. | No clipping/overlap, hidden essential actions, double scaling or lost state. Source view and GPUI overlays coexist correctly. Qualify real screen-reader access and real IME separately when available and authorized. |
| W16 CLI contracts | Use disposable sessions for open-at-position, file/directory pick and cancel, and open --wait. Interact with the native picker/editor; Save, Cancel, Finish, Discard and Save As abandonment on separate requests. | Exact picker output/exit status; waiting ownership and byte validation follow the CLI contract. Saving alone does not finish. Track callers and GUI processes separately. |

Use [product acceptance](../glimpse.md#correctness-and-release-gates) for additional filesystem and lifecycle cases. The tour is a coverage map, not proof that all faults have been tested. For a full tour, reach every command/control/category or explicitly list it as unverified. Keep a control inventory alongside full-tour results so omitted surfaces cannot disappear inside a broad pass label.

### Capture and measurement matrix

Default comparison viewports are 1280×800, 960×700 and 520×700 logical points when supported by the display. These are evaluation choices, not product size requirements. Record actual dimensions and minimum supported size; do not silently substitute a larger window. Capture both themes for directory lists, source, Markdown, search, Find/Replace, settings and conflict. At narrow width include open menus/dialogs; at larger text include long names and tab overflow. Check both densities and focus/hover/disabled/selected/modified states without requiring the full Cartesian product for every iteration.

Keep four separate result groups: appearance, usability, functionality/safety, and performance. None can compensate for a failure in another. For UX record completion, unnecessary actions, wrong-scope searches, context loss, focus repairs, surprises and explanatory help needed. An informed agent completing a memorized tour does not establish first-use discoverability or human preference.

For performance use the existing budgets and workloads. Record release build, machine/display, file/row sizes, cold/warm conditions, repetitions and instrumentation boundaries. Separate first results from completion, active from idle CPU, total memory from any justified breakdown, and GUI readiness from physical presentation. Run measurements with computer-use activity and other reviewers stopped. Repeat a surprising result under comparable conditions. Tool-call duration and screenshot timing are not input-to-present latency. Synthetic frames, nonactivating launches and Unicode paste cannot qualify physical 120 Hz, visible launch or IME respectively. Carry existing failed gates forward until replacement evidence actually closes them.

## Native coherence rubric

For each applicable surface, record `coherent`, `mismatch` or `unverified` against the following criteria, with evidence. A mismatch needs a concrete explanation; these labels are structured judgments, not objective measurements of taste.

| Criterion | Questions to answer against the declared criteria |
| --- | --- |
| Composition | Do toolbar, tabs, navigator and document form one window? Is content dominant, with clear location and active-document identity? |
| Typography and geometry | Are actual font faces, weights, baselines, row rhythm, padding and optical alignment consistent? Are controls comfortably readable at both densities? |
| Controls and symbols | Do shapes, strokes, icon sizes, labels and hit targets belong to one family? Are familiar actions recognizable without explanatory tooltips? |
| Materials and color | Do surfaces and elevations establish hierarchy? Are light/dark treatments coherent, readable and restrained, including opaque fallback? Verify rendered contrast rather than inferring it from a palette. |
| State | Are focus, selection, hover, disabled, preview, modified, conflict and partial coverage distinct and consistent? Does inactive selection remain understandable? |
| Menus and dialogs | Are grouping, labels, dismissal, keyboard containment and return focus familiar? Do secondary surfaces meet the same standard as the main window? |
| Reading and source | Do reading measure, headings, tables, code, source gutter and source text support their different tasks without excessive chrome? |
| Interaction continuity | Do resizing, navigation, tab switching, overlays and return paths preserve intent and context? Are motion and response immediate without becoming distracting? |

## Comparison and development loop

1. **Establish the evaluator.** Freeze task outcomes, fixture manifest, criteria and evidence set, comparison dimensions and required quality gates before implementation. Add newly discovered edge cases, but never remove a failing case to obtain a pass. Record any evaluator change and rerun affected baseline comparisons. Preserve evidence outside the implementation patch.
2. **Identify concrete gaps.** Compare the native baseline with the declared criteria. Keep a private defect list with scenario ID, screenshot/action evidence, severity, interface or accessibility principle, proposed correction and observable acceptance condition. Distinguish observation, interpretation and taste. “Does not feel native” needs specifics: typography, alignment, hierarchy, state treatment, focus or platform behavior.
3. **Choose a coherent batch.** Preserve file correctness and accessibility first, responsiveness/clarity next, then convenience and polish. Fix shared typography, geometry or components consistently across surfaces. Existing feature requirements can be repaired within the authorized scope; adding IDE features or rewriting the toolkit is not a visual-polish shortcut.
4. **Implement and verify.** One durable owner handles coupled implementation, diagnosis, appropriate automated checks and native verification. Repeat affected scenarios after each batch and compare identical states. Keep the best verified candidate recoverable. Before handback run the affected scenarios and relevant README checks; use the complete tour for broad changes or release qualification. Report unexecuted cases honestly rather than marking them passed.
5. **Check appearance and interaction.** The owner compares full-window captures, including secondary states, with the criteria and evidence set and verifies workflow and safety outcomes through native execution. Use a separate reviewer only for a specific consequential uncertainty or an explicit user request. Label evidence-only review; it does not establish native execution.
6. **Resolve findings.** Test findings, fix confirmed defects and rerun affected checks. Request another review only for an unresolved consequential concern, with the prior objection and new evidence. Agreement or a numerical style score is not verification.

The same owner may implement and perform native verification; serialize desktop input and measurements. If a reviewer is used, it must not edit the implementation or evaluator, and desktop control requires an explicit handoff. Sustained campaign execution continues toward the authorized objective within its resource and pause controls.

### Optional reviewer brief

Give each reviewer the task/design constraints, candidate identity, scenario results, original baseline/candidate captures, criteria and evidence set and measurement limits. Ask:

> Identify the strongest remaining evidence that this candidate falls short of a cohesive native desktop experience in your assigned area. For each finding, give the scenario/surface, observed defect, supporting evidence, user consequence, interface or accessibility principle, severity and a falsifiable acceptance condition. Separate verified defects, subjective preferences and unavailable evidence. Do not infer behavior from screenshots or claim literal indistinguishability. Report meaningful improvements as well as remaining gaps. Do not edit files, expand scope or operate the desktop without an explicit handoff.

### Completion and stopping

The ambition is release-quality native desktop behavior across the declared surfaces and interactions, while retaining Glimpse's identity. Evidence supports a bounded judgment of native coherence, not proof of universal indistinguishability or user satisfaction.

A candidate is ready for handoff when the core task path adds no unnecessary setup or decisions, required scenarios have recorded outcomes, changed functionality passes appropriate checks, no new safety/accessibility/performance regression remains unexplained, and appearance and interaction findings have concrete dispositions. Serious unresolved defects prevent a completion claim; blocked/unverified checks remain explicit. Pre-existing failed gates cannot be relabelled as solved by a UI campaign.

For an explicitly authorized overnight run, respect its actual deadline/budget and reserve time for integration, verification and cleanup. If no duration is supplied, perform a bounded pass rather than inferring indefinite authority. After repeated iterations produce no verified improvement, reassess the diagnosis, alternatives and evidence; continue with a promising authorized approach or report a real blocker or diminishing returns. Do not broaden the product or manufacture cosmetic changes to stay busy. At a boundary preserve the best verified candidate and state remaining work, even when the aspiration has not been achieved. Routine implementation choices need no repeated user approval; an essential blocker needs a real pending structured question while independent authorized work continues.

Before handoff, stop only owned processes, restore altered personal configuration, and remove disposable fixtures/builds/logs after checking ownership and recoverability. Preserve concise before/after evidence, useful measurements, rollback and unresolved recovery data. Use storage-steward after storage-heavy work. Do not remove shared caches or other sessions. Update the existing private checkpoint with outcome, next action, evidence and live ownership. Commit/push/install/merge only within their separately established authority.

The handoff should link the runnable candidate and evidence, summarize user-visible changes, report scenario/check results and remaining failed or unverified gates, and distinguish evidence-only review from actual native interaction. Keep raw reviewer reports and action logs out of published documentation.
